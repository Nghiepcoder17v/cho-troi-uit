# UI audit baseline — 2026-11-11

## Scope and method

Read-only source audit for FE-0 in `BBPL_Cho-Troi-UIT_Roadmap_2026-11-11.md`. Reviewed the current React/Vite app shell, marketplace, product card/detail, sell form, Account Center, public profile, cart, auth modal, styles, API contract, README and `docs/DESIGN_PROFILE.md`. No application files or user data were changed by the audit. No browser session was started; responsive appearance and runtime states below are therefore not claimed as visually verified.

## Existing reusable foundation

- Dark/light CSS variables already cover surfaces, text, borders, accents, semantic states, focus, overlay, shadows and common radii. The graphite/lime/cyan identity matches the approved Design Profile.
- Shared `AppShell`, `ProductCard`, `ProductDetailModal`, `CartDrawer`, `AuthModal`, `ReviewList`, account panels, theme hook and formatter exist.

## Findings

Severity describes user impact and roadmap priority, not a claim that automated accessibility or visual testing was run.

| Severity | Finding | Evidence / impact |
|---|---|---|
| High | Marketplace landing and product discovery are combined; no dedicated Explore view exists. | `AppView` only has `market`, `sell`, `account`, and `public-profile`; `MarketPage` combines hero, categories and listing. It supports keyword/category and pagination, but not server-side price/condition/sort filters. |
| High | Product cards, detail, and cart use decorative glyphs as product imagery. | `ProductCard`, `ProductDetailModal`, `CartDrawer`, and account cart render glyphs selected from product ID. This is not a real image or an explicit neutral “no image” fallback; media API/schema work is a prerequisite to real product photos. |
| Medium | Password-change form is always rendered in Account Settings. | `AccountSettings` immediately renders the three password fields; the roadmap asks for an explicit “Đổi mật khẩu” action before showing the form. API reuse is already available. |
| Medium | Theme control appears in both the global top bar and Account Settings. | `AppShell` renders `ThemeToggle`; `AccountSettings` also renders a theme control. The roadmap calls for keeping the control in settings only. |
| Medium | Overlay semantics and keyboard lifecycle need verification and likely improvement. | Cart/detail/auth overlays are custom backdrop elements. Source review did not establish consistent dialog naming, `aria-modal`, Escape handling, focus containment/restoration, or background inertness. Keyboard/screen-reader behavior must be checked before changing shared overlay patterns. |
| Medium | Marketplace lacks explicit loading and fetch-error presentation in its page component. | `MarketPage` handles result/empty/pagination but receives no loading/error props. Any global shell notice is transient and may not explain a failed listing load or offer retry. Confirm the request lifecycle in the browser before prioritizing implementation. |
| Low | Shared design foundation exists but is concentrated in a large stylesheet with repeated component-specific sections. | `styles.css` is over 2,700 lines and contains later appended account/profile styles. Consolidate only while introducing tokens/components with regression review; avoid a blanket rewrite. |
| Low | UI component directory is untracked in the checkout. | `frontend/src/components/ui/` exists outside Git's tracked baseline. Its contents may be in-progress user work; excluded from findings about shipped/reusable components and must be preserved. |

## Screen and state coverage from source

- **Marketplace:** hero/search, categories, result count, product grid, pagination and empty result state. Loading/error and mobile visual behavior were not verified in a browser.
- **Product detail:** modal with product metadata, seller link, reviews and add-to-cart state; no real media data in the API contract.
- **Sell:** title, price, condition, category and description; no image selection, preview or upload because media API is not implemented.
- **Account Center:** overview, own listings, purchases/sales, cart and settings; account subsections and narrow layouts have CSS breakpoints.
- **Public profile:** profile summary, product status filter and reviews; current API omits avatar and bio.
- **Authentication/cart:** custom modal/drawer and empty-cart states; overlay keyboard/accessibility behavior needs runtime confirmation.
- **Theme/motion:** dark and light token sets and `prefers-reduced-motion` exist. Contrast pairings and focus visibility across every component have not been measured.

## Proposed next scope (FE-1)

1. Keep the approved graphite/lime/cyan identity and the existing semantic token system; inventory token gaps and duplicated rules before changing CSS.
2. Agree on a small reusable UI pattern set (button, field, badge, card, dialog, toast, skeleton and empty state), then migrate representative shared controls rather than replacing the whole stylesheet.
3. Move theme switching out of the top bar and make password change an explicit, dismissible security action that clears password state on close.
4. Address the overlay keyboard/accessibility lifecycle as a shared pattern and record manual keyboard checks.
5. Defer real product photos, avatar/bio, Explore advanced filters and transaction timeline to their backend dependencies; do not present mock data or inactive controls as implemented features.

## Not verified

- Desktop/tablet/mobile visual render, both themes, real focus order, contrast ratios, screen-reader output, dialog focus management, API loading/error behavior, authentication and purchase regression.
- No backend/database behavior was modified or tested. No automated tests, lint, or build were run during this read-only audit.
